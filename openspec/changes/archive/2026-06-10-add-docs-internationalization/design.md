## Context

The docs app is a Docusaurus 3 application under `apps/docs`. Its current configuration sets `defaultLocale: 'es'` and `locales: ['es']`, and `docusaurus-lunr-search` is configured only for Spanish. Documentation content lives under `apps/docs/docs`, uses autogenerated sidebars from the filesystem, and includes category metadata files for the current Spanish structure.

Docusaurus already provides native filesystem-based i18n for docs content, theme/UI labels, navbar items, footer content, and generated metadata. This change should use that built-in mechanism rather than introducing a custom translation runtime for the docs app.

## Goals / Non-Goals

**Goals:**
- Make the docs site available in Spanish, English, and Portuguese.
- Keep Spanish as the default locale and preserve the current Spanish docs structure and routes.
- Add English and Portuguese translations for all existing documentation pages and category metadata.
- Localize Docusaurus UI strings, navbar labels, footer text, and site metadata that users see.
- Keep docs search usable across the supported languages.
- Verify the docs app with typecheck and build commands when dependencies are available.

**Non-Goals:**
- Changing backend, web app, Prisma, Docker, or shared package behavior.
- Introducing runtime language selection behavior into `apps/web`; that is covered by the separate web internationalization capability.
- Rewriting the documentation content beyond translation and small terminology adjustments required for natural English and Portuguese.
- Adding machine translation services or translation management platforms.

## Decisions

1. Use Docusaurus native i18n directories for localized content.

   English and Portuguese docs will live under `apps/docs/i18n/en/docusaurus-plugin-content-docs/current` and `apps/docs/i18n/pt/docusaurus-plugin-content-docs/current`, mirroring `apps/docs/docs`. This matches Docusaurus conventions, keeps the Spanish source docs canonical, and avoids custom loaders.

   Alternative considered: duplicating content in top-level `docs-en` and `docs-pt` plugin instances. That would add routing and sidebar complexity without improving the user experience.

2. Keep Spanish as the default locale and add English and Portuguese to the Docusaurus config.

   `i18n.locales` should become `['es', 'en', 'pt']`, with locale labels and html language values configured as needed. Spanish remains the unprefixed default route, while non-default locales use Docusaurus locale-prefixed routes.

   Alternative considered: making English the default because it is common in technical docs. That would be a breaking documentation URL change and would move away from the current Spanish-first documentation.

3. Store localized UI/theme labels in Docusaurus translation JSON files.

   The implementation should generate or maintain locale files under `apps/docs/i18n/en` and `apps/docs/i18n/pt` for code/theme translations, navbar text, footer text, and other Docusaurus-generated labels. This keeps translated UI copy near the locale content and follows the existing `write-translations` workflow.

   Alternative considered: conditional logic in `docusaurus.config.ts` to switch strings by locale. Docusaurus translation files are more maintainable and avoid mixing locale resources with configuration logic.

4. Configure search for all supported languages using the existing Lunr plugin.

   The existing `docusaurus-lunr-search` dependency already supports `lunr-languages`; the search plugin should include Spanish, English, and Portuguese language support. If plugin limitations appear during implementation, prefer the smallest configuration change that produces working builds and document any limitation in the implementation notes.

   Alternative considered: replacing Lunr with another Docusaurus search plugin. That would increase scope and dependency risk for a docs i18n change.

## Risks / Trade-offs

- Translation drift between Spanish source docs and localized docs -> Keep the folder structure mirrored and include task checks that every Spanish doc has English and Portuguese counterparts.
- Generated Docusaurus translation files may change between Docusaurus versions -> Commit only the locale files needed by the current app and verify with `pnpm docs:build`.
- Search language configuration may be constrained by the Lunr plugin -> Validate during build and keep the existing plugin unless it blocks multilingual builds.
- Manual translations can contain terminology inconsistencies -> Use product names consistently (`Capture ACV`, `ACV Compare`, `openLCA`) and preserve command names, paths, API names, and code snippets verbatim.
- Non-default locale URLs change the path shape for English and Portuguese -> Rely on Docusaurus default locale routing and preserve Spanish default URLs.
